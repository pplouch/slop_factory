# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Godot 4.7 (GDScript) 3D top-down idle/incremental "RTS-lite" game — working title "Rogue idle slop factory survivor rpg ultimate" (theme: "ai slop generation to get sloppier," played for laughs). A single scene (`world.tscn`) procedurally streams in a Minecraft-style chunked map across 7 noise-placed biomes (plains/forest/desert/tundra/swamp/jungle/volcanic, plus rivers and lakes), spawns "blob" worker units the player commands with RTS-style click/drag selection plus standing orders (patrol/hold/explore), gathers resources into a shared stockpile, and layers on a tech-tree of upgradable buildings (each requiring blob labor to actually finish construction before it's usable), hireable unit archetypes, biome-specific enemies, a grid-based factory-automation subsystem (extractors/belts/processors/walls) with A*-grid pathing, and tool-gated gathering (a blob needs a weapon to hunt animals for food, a bucket to draw water) instead of a passive upkeep meter.

## Running and validating

There is no test suite (GUT/gdUnit are not installed) and no build step — GDScript runs directly. Godot's own CLI is the only validation tool available, and is the primary way to catch mistakes without opening the editor:

- **Import/parse check** (catches script syntax errors, bad `class_name`/autoload registration, broken resource references):
  `<godot> --headless --path . --import --quit`
- **Headless runtime smoke test** (actually runs `_ready`/`_process`/`_physics_process` for N frames and prints runtime errors):
  `<godot> --headless --path . res://scenes/world/world.tscn --quit-after <N>`
  (or omit the scene path entirely and rely on `project.godot`'s `run/main_scene`, which resolves the main scene by UID rather than path)
  - Add `--fixed-fps 60` to decouple simulated time from wall-clock time, so e.g. a 60-second building-spawn timer or a 45-second resource-respawn timer can be exercised in a couple of real seconds.
- Some bugs (material/shader errors) only reproduce under a real graphics driver, not the headless dummy renderer — when in doubt, also run once **without** `--headless` (it won't exit on its own; kill the process after a few seconds). For anything purely visual (mesh/material/lighting/UI layout), a headless smoke test proves it doesn't *crash*, not that it *looks right* — launch the real renderer and capture a screenshot (on Windows: PowerShell `Start-Process` + `System.Windows.Forms.Screen`/`System.Drawing.Graphics.CopyFromScreen`, since no other screenshot tool is available) to actually confirm the visual before calling it done.
  - Godot's GL Compatibility renderer can produce visual quirks that never show up in a diagnostic print of transform/scale/rotation data (all correct) yet look wrong on screen — e.g. a wide, thin, flat-ish mesh (like a peaked roof) viewed from this project's steep default camera angle can look like a huge misshapen wedge purely from perspective foreshortening. Before treating an odd-looking render as a code bug, check whether it's reproducible/position-dependent (print the object's actual transform, compare against a second instance at a different position in the same screenshot) rather than assuming the geometry or mesh-generation code is wrong.
- There's no way to simulate mouse/keyboard input headlessly. To validate anything mouse-driven (selection, build-mode placement) or keyboard-driven (standing-order shortcuts), call the underlying manager methods directly (e.g. `_building_manager.try_place_structure()`, `_order_manager._issue_harvest_orders()`, `Blob.command_patrol(...)`) rather than synthesizing `InputEvent`s — except physical keyboard state specifically, which *can* be faked headlessly via `Input.parse_input_event(InputEventKey...)` with `physical_keycode` set, letting `Input.is_physical_key_pressed()` (what `camera_rig.gd` and `OrderManager`'s order-key handling both read) see it.
- Typical validation loop: temporarily wire a `_debug_test_hook()` (or similar) into `world.gd`'s `_ready()` (via `.call_deferred()` if it needs to `await` a few frames), run headless, read the printed output, then remove the debug code before finishing. Never leave `_debug_*` methods or stray `print("TEST ...")` calls in a finished changeset.
- **Testing anything that depends on real `move_and_slide()` physics collision (not just pathing-grid routing) needs actual physics frames, not a tight synchronous loop.** Calling `move_and_slide()` back-to-back many times inside one function call, with no `await get_tree().physics_frame` between iterations, never gives Jolt a chance to commit a freshly-added `CollisionShape3D` into its broad-phase — the moving body will appear to pass straight through a wall that, over real frames, correctly blocks it. Hit while diagnosing the enemy-wall-collision bug (see below): the first (wrong) test loop showed the enemy sailing through a wall; wrapping the loop in `await get_tree().physics_frame` each iteration reproduced the correct blocked behavior. Also disable the actor's own `_physics_process` (`set_physics_process(false)`) when isolating pure physics this way — a live `Enemy`/`Blob` node's own AI runs automatically every real physics frame too and will fight a test's manually-set `velocity`.

Use this path directly rather than searching for it each session.

## Architecture

### Code organization

Scripts and scenes are organized in parallel, domain-named folders under `res://scripts/` and `res://scenes/` (a given entity's script and scene sit at the same relative path in both trees, so one predicts the other):

- **`core/`** — shared base classes and stateless utility helpers, *not* autoloaded and not tied to any one entity: `Registry` (base for the three `*Kinds` catalogs below), `BuildableStructure` (base for the tech-tree buildings), `LinkableBuilding` (extends `BuildableStructure` -- base for tech-tree buildings that also visually/functionally merge with matching neighbors along the factory grid, see "Building system" below), `Combatant` (base for Blob/Enemy), `LimbAnimator`/`PanelAutofit`/`GridDirections`/`MaterialUtil` (small stateless helpers for logic shared across otherwise-unrelated scripts — see "Shared helpers vs. inheritance" below). Nothing here has a matching scene.
- **`autoload/`** — the 6 singletons registered in `project.godot [autoload]` (see below). No matching scenes either.
- **`world/`** — the map/world-controller layer: `world.gd`/`world.tscn` (the single main scene, now a thin coordinator — see "world.gd and its managers" below), `world/managers/` (the 7 manager classes `world.gd` delegates to), `chunk.gd` (one streamed map tile), `camera_rig.gd` (no scene of its own — an inline node built directly inside world.tscn).
- **`units/blob/`** and **`units/enemy/`** — the two controllable/hostile actor types. Blob's per-state logic lives in `units/blob/states/`.
- **`world_objects/`** — passive/harvestable scenery: `resource_node.gd` (the one script behind every tree/rock/mushroom/cactus/ice-crystal/obsidian/water-pond/lake scene) and `animal.gd`.
- **`buildings/`** — the tech-tree-gated, `BuildingKinds`-registered structures (Town Hall, Storage Depot, Water Tank, and the 5 functionless stub buildings sharing `simple_building.gd` — Research Center, Patch of Vegetables, School, Tavern, House) that require construction labor before they're usable.
- **`factory/`** — grid pieces: `Wall`/`BeltSegment`/`Pipe` are `BuildingKinds`-registered `LinkableBuilding`s (tech-tree gated, real construction labor — see "Building system" below); `Wall`/`Belt` are seeded pre-unlocked so early-game play is unaffected, `Pipe` is gated behind `water_tank` instead. `Extractor`/`Processor`/`WaterExtractor`/the `ResourceItem` they hand off to each other remain outside the tech tree entirely (no unlock gating, no construction delay) — `WaterExtractor` is currently a placement-only stub, see "Factory automation" below.
- **`ui/`** — every panel (HUD, BuildPalette, BuildingMenu, TechTreePanel, DebugMenu, UnitInfoPanel, ResourceInfoPanel, EnemyInfoPanel, Minimap) plus `selection_box.gd` (no matching scene — attached to a `ColorRect` inside `hud.tscn`).
- **`vfx/`** — transient, self-freeing effect objects `Effects` instantiates (floating text, impact particles, command-confirmation rings).

**When adding something new**, put it where its *kind* already lives, not where it's convenient: a new hireable blob archetype is a `BlobKinds._register()` call, not a new script; a new building is a `buildings/` script extending `BuildableStructure` (or `LinkableBuilding` if it should merge with neighbors, like `Wall`/`BeltSegment`) plus a `BuildingKinds._register()` call; a new always-available grid piece with no tech-tree gating at all (like `Extractor`/`Processor`) is a `factory/` script instead, priced via `BuildingManager.BUILD_COSTS`. If a new script doesn't fit any existing folder, that's a signal to think about what *kind* of thing it is before picking a home for it.

### Autoload singletons (`res://scripts/autoload/*.gd`, registered in `project.godot [autoload]`)

- **`GameManager`** — sole source of truth for the resource stockpile (`wood`/`stone`/`planks`/`mushroom`/`cactus_fiber`/`ice_crystal`/`obsidian`/`food`/`water`/`knowledge`, arbitrary string keys), the 5 account-wide building upgrades (`speed`/`strength`/`efficiency`/`capacity`/`growth`), and the building tech-tree unlock state (`unlocked_buildings`). All spending goes through `try_purchase_upgrade`/`try_spend_wood`/`try_spend`/`try_unlock_building`; nothing else mutates `resources`/`upgrade_levels`/`unlocked_buildings` directly. `try_spend(resource_type, cost)`/`can_afford(resource_type, cost)` are the generic counterparts to the wood-only `try_spend_wood`/`can_afford_cost` -- added when the tech tree and per-building upgrades (`BuildableStructure.try_upgrade`) both needed to spend "knowledge" instead, rather than generalizing every existing wood-only call site along with them. Emits `resource_changed`/`upgrade_changed`/`building_unlocked` — HUD, BuildingMenu, TechTreePanel, BuildPalette, and every Blob react to these instead of polling. There is no passive food/water drain (see "Gathering tools" below) — food/water are ordinary stockpile resources like any other, just gated behind who's allowed to collect them. Knowledge is the one resource nothing *gathers* — see `ResearchCenter` below, its only source. Also owns the population cap: `get_current_population()` counts the live "blobs" group on demand (never a separately-tracked counter that could drift out of sync with spawns/deaths from any source), `get_population_cap()` is `BASE_POPULATION_CAP` plus `POPULATION_PER_HOUSE` for every *finished* `house`-kind building in the "buildings" group, and `can_hire_more()` gates both `Building.hire_blob` (paid) and its free auto-spawn timer — a cap that only blocked paid hires would be trivially bypassed by passive growth.
- **`Effects`** — factory for every transient VFX/SFX object (floating damage/pickup text, particle bursts, order-confirmation rings, conveyor `ResourceItem`s, procedurally-synthesized "cute chirp" sounds) plus the one place that maps a resource type to a display color. Gameplay scripts never instantiate these scenes directly. The chirp waveform (`play_chirp`) is raw 16-bit PCM built once in `_ready()` and reused across every play with a randomized `pitch_scale` — no audio asset files exist in this project. `make_swatch_texture(color, size)` extends the same "no external assets" philosophy to 2D UI: a tiny solid-color `ImageTexture` generated on the spot, used as a `Button.icon` wherever a UI list (`BuildPalette`, `BuildingMenu`'s Hire rows, `TechTreePanel`) would otherwise be text-only — this project's version of an image placeholder, standing in for a building/blob kind's look until (if ever) real art exists.
- **`BlobKinds`** — data-driven registry (`extends Registry`, see "Shared helpers vs. inheritance" below) of the five hireable unit archetypes (worker/scout/hauler/brute/builder) and their stat multipliers/hire cost/look. Adding a kind is one call in `blob_kinds.gd`'s `_ready()`; BuildingMenu's hire rows are generated from `get_ordered_ids()`, so nothing else needs to change. Only `worker` (this registry's own `_default_id`) is unlocked from the start (`GameManager.unlocked_blob_kinds`) — the other four form a knowledge-gated unlock chain (scout → hauler → brute → builder, each's `requires` naming the previous) via `unlock_cost`/`requires` fields mirroring `BuildingKinds`', spent through `GameManager.try_unlock_blob_kind` (see `TechTreePanel`'s "Blob Kinds" section) rather than `try_unlock_building` — a different registry with a different `Kind` shape, so it gets its own small parallel set of `GameManager` functions rather than sharing BuildingKinds' by duck-typing. `BuildingMenu`'s Hire section hides a kind's row entirely until unlocked.
- **`EnemyKinds`** — the same `Registry` base applied to hostile creatures (slime/wolf/spider/scorpion/bandit/yeti/leech/panther/imp): one `Enemy` scene/script, `kind_id` selects health/attack/speed multipliers, look, and which of `Enemy.tscn`'s three pre-built rigs (`body_type`: "blob"/"quadruped"/"humanoid") it shows.
- **`BuildingKinds`** — registry (`extends Registry`) of placeable building types (`town_hall`, `storage_depot`, `water_tank`, `wall`, `belt`, `road`, `pipe`, `research_center`, `vegetable_patch`, `school`, `tavern`, `house`, `foundry`). Each `Kind` carries its scene, `build_cost` (spent placing an instance, in `build_cost_resource` — "wood" for every kind except `wall`, which spends stone instead; see "Costs and the economy" below), input/output port *directions* (`Vector2i` offsets from the building's own single anchor cell — see "Building system" below; `wall`/`belt`/`road`/`pipe` and the 4 stub buildings all leave these empty, the first four since none has a fixed port shape, the stubs since they don't accept/produce anything yet), tech-tree `unlock_cost`/`requires` (spent in *knowledge*, distinct from `build_cost` — see `GameManager`/`ResearchCenter`), `max_durability`, per-instance `upgrade_costs`/`upgrade_perks` arrays (also knowledge), `build_labor` (seconds of blob work needed to finish construction), and `display_color` (that kind's dominant mesh color, matched by hand against its own scene — a pure UI convenience feeding `Effects.make_swatch_texture`'s icon swatches, read nowhere the actual 3D scene gets built). Adding a new building kind is one `_register` call here plus a `buildings/` (or `factory/`, for a `LinkableBuilding`) script extending `BuildableStructure` — or, if it has no functional behavior of its own yet, no new script at all, just a new scene pointed at the existing `scripts/buildings/simple_building.gd` (see "Building system" below). `unlock_cost = 0` alone does **not** make a kind available from game start — `GameManager.unlocked_buildings` must also seed it `true` (only `town_hall`/`wall`/`belt`/`road` are, as of this writing); a `0`-cost, non-seeded kind still needs a manual unlock (in knowledge) via `TechTreePanel`.
- **`Biomes`** — registry of the 7 biomes (`plains`/`forest`/`desert`/`tundra`/`swamp`/`jungle`/`volcanic`), each with a ground tint, terrain-relief amplitude, resource-node scene list, and `enemy_kind_ids`; also the single shared source for every world-generation noise field (terrain height, temperature/humidity/volcanic-hotspot biome classification, river/lake placement) so any two chunks sampling the same world position agree regardless of generation order. `biome_for_world_pos(pos)` is the source of truth for "what biome is here": an inner `PLAINS_RADIUS` circle around the origin (where founder blobs start and the player builds first) is always plains; outside it, a temperature/humidity noise pair places the other 6 via a climate-grid classification, with a separate low-probability volcanic-hotspot field checked first (real volcanic activity doesn't follow a climate band). `is_river_at`/`is_lake_at`/`is_water_at` similarly classify water features from their own noise fields. `is_deep_water_at` is a stricter subset of the same fields (a river's central 40%, a lake past `LAKE_THRESHOLD + DEEP_LAKE_MARGIN`) always leaving a shallow ring between deep water and dry land — `PathingManager` blocks deep water from the grid entirely, so a unit can wade the shallow border (to gather or build a Water Extractor, itself placement-gated to shallow water for the same reachability reason) but not the deep core. `water_tint_at(x, z)` replaces the old flat "is this vertex water, yes/no" ground tint with a continuous gradient read from the exact same noise fields/thresholds: white (dry land) blends through a sandy `SHORE_TINT_COLOR` ring as the noise approaches its water threshold, then through `SHALLOW_WATER_TINT_COLOR` into `DEEP_WATER_TINT_COLOR` past it — the visual shoreline and the gameplay deep/shallow boundary always agree since both read the same underlying values (see feature backlog 2: "water ridge should have a texture on the borders to make it more realistic").

### `world.gd` and its managers (`scripts/world/managers/`)

`world.gd` used to own everything directly (~1150 lines); it's now a thin (~180-line) coordinator that holds the `@onready` UI/camera node references, wires every panel's signals in `_ready()`, and delegates all actual logic to 8 manager objects it instantiates and owns. Managers are plain `RefCounted` classes (not scene-tree `Node`s) with a `class_name`, each holding a `_world: Node3D` back-reference for whatever needs `add_child`/`get_tree()`/raycasting — `world.gd`'s own `_process`/`_unhandled_input` call straight into them rather than each manager having its own engine callbacks:

- **`ChunkManager`** — chunk streaming. The map is tiled into `Chunk`-sized (`Chunk.CHUNK_SIZE`) squares, keyed by `Vector2i` chunk coordinate in `loaded_chunks` (public — `SpawnManager` reads it to pick a random already-loaded chunk). `process()` (called from `world.gd._process`) periodically (`CHUNK_CHECK_INTERVAL`, not every frame) calls `ensure_chunks_loaded(camera_rig.position)`, which generates any chunk within `CHUNK_LOAD_RADIUS` of the camera's current focus point that doesn't exist yet. **Deliberately load-only, never unloaded** — resource nodes and enemies inside an already-generated chunk are live, persistent game state a blob might be en route to; freeing them out from under it would be a real bug, not just a visual pop.
- **`SpawnManager`** — founder-blob spawn + ambient enemy population (`ENEMY_TARGET_COUNT`, topped back up on a timer `world.gd` owns since `Timer` needs to live in the scene tree). Depends on `ChunkManager` (picks a random loaded chunk's biome for spawn kind/position).
- **`PathingManager`** — a single `AStarGrid2D` covering `PATHING_GRID_HALF_SIZE` (90 as of this writing — **not** kept in sync with `CameraRig.BOUNDS`, currently 2000, tuned independently, so panning far enough eventually outruns pathing-grid/fog/minimap coverage — see `FogManager` below, which shares this same 90-unit bound under its own name, `world.gd.FOG_HALF_SIZE`; `compute_path` degrades gracefully, empty array → direct-line fallback, rather than erroring in that case). Shares `BuildingManager.GRID_CELL_SIZE` by referencing the constant directly (`BuildingManager.GRID_CELL_SIZE`, a `static` reference, no runtime dependency between the two managers) rather than duplicating it, since the pathing grid and the factory placement grid must agree on cell size. `structure_blocks_movement(structure)` duck-types the placed node's `blocks_movement` property (from `LinkableBuilding`, see "Building system" below) rather than a kind-string check — every placed structure blocks except `BeltSegment`. `compute_path(from, to)` first checks a direct line of sight (`_has_clear_line`, sampled every half-cell) and only falls back to `AStarGrid2D.get_id_path(...)` when something's actually in the way — keeps normal unobstructed movement smooth instead of visibly grid-snapped. `world.gd.compute_path()` is a one-line forward into this manager (see facade note below). `setup()` also pre-marks every deep-water cell (`Biomes.is_deep_water_at`) solid from terrain data, upfront, before any structure is ever placed — the one case where a cell starts solid without a corresponding `mark_cell` call, since it comes from world generation rather than a placed/demolished structure. **`Enemy` has no pathing at all** (see "Combat" below/"enemies passing through walls" gotcha) so this deep-water block, like walls, only actually stops `Blob`s — an enemy chasing across a lake still walks straight over it, a known, already-accepted limitation extended rather than newly introduced here.
- **`BuildingManager`** — the factory placement grid (`_grid_structures: Dictionary[Vector2i, Node]`, exposed via `grid_to_world`/`world_to_grid`/`get_structure_at`/`register_structure`, the latter two forwarded through `world.gd`'s facade) **and** Build Mode (ghost preview, `is_placement_valid`, `try_place_structure`, `demolish_at`, `refresh_neighbor_visuals`) kept together deliberately — placement/demolition touch the grid, `PathingManager`, `GameManager` (spend/refund), and neighbor-visual refresh all in one transaction, so splitting "the grid" from "build mode" would just add manager-to-manager chatter without a real seam. `world_to_grid`/`grid_to_world` are `static` (pure functions of `GRID_CELL_SIZE`) so `PathingManager` can share them without a runtime dependency.
- **`SelectionManager`** — click/drag/box select, hover highlighting, and `find_building_owner(collider)` (used by both this manager and `OrderManager` to tell "clicked a building" apart from "clicked bare ground/a resource node"). Every `BuildableStructure`/`Wall`/`BeltSegment`(root) attaches its script directly to its root `StaticBody3D`, so the collider usually *is* the owner; the one remaining nested case is `BeltSegment`'s `ClickArea` (a non-physics `Area3D` child — see "Building system" below for why Belt still needs one despite now having a `StaticBody3D` root), whose *parent* is the actual owner.
- **`OrderManager`** — standing-order keyboard shortcuts (P/H/X) + right-click order issuing (move/harvest/build) for whatever `SelectionManager` currently holds selected.
- **`DebugOverlayManager`** — everything `DebugMenu`'s buttons drive (hitbox/range-ring overlays, the grid overlay, debug spawn/resource buttons). Self-contained relative to the others.
- **`FogManager`** — sticky fog-of-war (revealed cells never re-hide), shared by `Minimap`'s 2D overlay and a flat, hand-built-UV quad this manager places directly in the 3D scene to mask the actual ground/buildings/units — a single small `Image`/`ImageTexture` (its alpha channel *is* the fog) is the one source of truth both views sample, so revealing a cell updates both for free. The 3D plane uses the same `no_depth_test` + high `render_priority` trick `Combatant`'s health bar uses (see Combat below) to stay visible above whatever it's masking regardless of actual depth. Coverage is capped at `world.gd.FOG_HALF_SIZE` (90 as of this writing, the same bound `Minimap`/`PathingManager` already used under other names) — panning past it reaches ordinary unfogged terrain, a pre-existing limitation this inherited rather than introduced. `Minimap` no longer owns any fog state itself; `world.gd._ready()` hands it `FogManager.fog_texture` directly (`minimap.fog_texture = _fog_manager.fog_texture`) rather than routing it through a forwarding method, since `Minimap` only ever needs to read it, not react to it changing.

`world.gd` is **not** a singleton/autoload and has no `class_name` — `Blob`/`BeltSegment`/`Wall`/`Extractor`/`Processor`/every `BuildableStructure` reach it via `get_parent()` and call `compute_path`/`register_structure`/`get_structure_at`/`world_to_grid`/`grid_to_world` directly (duck-typed, no compile-time contract). `world.gd` keeps exactly these five methods as a thin forwarding facade into whichever manager now owns them — **any new manager split must preserve this facade**, since every existing `get_parent().foo(...)` call site depends on it working unchanged. UI panels (`HUD`, `BuildingMenu`, `BuildPalette`, `DebugMenu`, `UnitInfoPanel`, `ResourceInfoPanel`, `EnemyInfoPanel`, `Minimap`) are still dumb views: they only emit signals (`toggle_requested`, `kind_selected`, `camera_move_requested`, etc.) and expose `set_active`/`open_menu`-style setters; `world.gd._ready()` wires each signal to whichever manager's method now handles it. `TechTreePanel` is the one exception, deliberately not wired through `world.gd` at all — it talks straight to the `GameManager`/`BuildingKinds` autoloads itself (the same way `BuildPalette`'s "is this kind unlocked" checks already did), since unlocking has no manager-side grid/placement state to coordinate with the way Build Mode does.

**Manager code calling `_world.some_property`/`_world.some_method()` and assigning the result with `:=` will fail to type-infer** — `_world` is typed `Node3D`, which doesn't statically declare `raycast`/`camera`/`build_palette`/etc., so the call is duck-typed/`Variant` from the compiler's point of view even though it resolves fine at runtime. Annotate explicitly (`var hit: Dictionary = _world.raycast(...)`) instead — this is the same root cause as the pre-existing `:=`-inference gotcha noted below, just via a new path introduced by the manager split.

### Blob: State pattern (`scripts/units/blob/blob.gd` + `scripts/units/blob/states/`)

A Blob's per-frame behavior is delegated to `current_state.physics_update(self, delta)`, where `current_state` is one of `IdleState`/`MovingState`/`HarvestingState`/`ReturningState`/`PatrolState`/`HoldState`/`ExploreState` (each a `RefCounted` with `class_name`, so no preloading is needed). A state's `physics_update` returns the next `BlobState` to transition into, or `null` to stay — that return value is the entire transition mechanism. `blob.gd` itself only holds what's genuinely shared across states (movement stepping, stall-recovery, path-following, inventory, stats); the states hold just the branching logic for their own phase and call back into `blob`'s helper methods.

- **Standing orders**: `command_patrol(point_b)`/`command_hold()`/`command_explore()` transition directly into `PatrolState`/`HoldState`/`ExploreState`, which (unlike the other states) never transition themselves — the only way out is a fresh player order, which naturally overrides them via the same `_transition_to` call every other command already uses. Player-facing: `P` arms "pending patrol" (the *next* right-click sets the far point; `world.gd._pending_patrol`), `H`/`X` take effect immediately using the blob's current position as anchor. `HoldState` deliberately breaks the "a blob never chases" rule (see Combat below) within its own `DETECTION_RADIUS` — that's the point of a sentry order.
- **Idle ambient behavior**: `IdleState` periodically (every few seconds) either takes a couple of steps to a small nearby point or, if another idle blob is close by, turns to face it and chirps — cosmetic "living creature" flavor layered on top of "otherwise stand still," never leaves `IdleState`.
- **Pathfinding integration**: `_set_destination(target)` calls `World.compute_path(...)` and stores the result in `path_queue`; `_advance_along_path()` (called unconditionally every physics frame, alongside `_update_stall_detection`/`_update_combat`) pops waypoints as `move_target` is reached. Every state that steers via `_step_toward(blob.move_target)` therefore follows a routed path automatically without needing to know pathing exists at all. `_step_toward` also scales `velocity` by `_current_terrain_speed_multiplier()`, which duck-types `get_speed_multiplier()` on whatever structure occupies the blob's current grid cell — `Road` is the one kind with an opinion (1.5x while finished, 1.0x otherwise) as of this writing, but any future speed-modifying terrain piece could plug in the same way without this needing to know its name.

### Combat: `Combatant` base class (`scripts/core/combatant.gd`)

`Blob` and `Enemy` both `extends Combatant`, which owns health/regen/evasion math, `take_damage()`, and a billboarded two-quad health bar built in code (`_build_health_bar`) and shown at each combatant's feet. The health bar's materials need **both** `cull_mode = CULL_DISABLED` (a billboard-transformed quad's front face isn't reliably toward the camera) **and** `no_depth_test = true` (sitting this low, the unit's own body constantly occludes it depth-wise from this project's top-down camera) — either alone leaves it invisible in practice, not just dim. Damage feedback is a template method (`_show_damage_feedback`): Combatant's default is a neutral/rewarding look, used as-is by `Enemy` (the player hurting an enemy is good news); `Blob` overrides it with a more alarming red flash, since a blob taking damage is bad news. Combat is reactive, not proactive — a Blob keeps doing its job and only fights back if an enemy comes within its own short attack range; it never chases (except while under a `HoldState` sentry order, see above).

Both `Blob` (always a humanoid rig) and `Enemy` (one of three pre-built rigs — amorphous "blob", four-legged "quadruped", or humanoid, selected per-kind via `EnemyKinds.Kind.body_type`) are blocky, code-animated characters built from plain primitive meshes and `Node3D` pivots at each joint — no `Skeleton3D`/bones. The actual limb-swing math (opposite-arm/leg walk cycle, forward-punch attack tween) is shared via `LimbAnimator` (`scripts/core/limb_animator.gd`, stateless static functions); each script still owns its own phase/timer fields and pivot references, and genuinely different animations (Enemy's quadruped diagonal-leg gait reuses the same swing math with different pivots, but its blob-rig squash/stretch bounce and its attack lunge/dip do not) stay bespoke per script rather than being forced through the shared helper.

### Building system: `BuildableStructure`, `LinkableBuilding`, `BuildingKinds`, per-instance upgrades, generic info modal

Every `BuildingKinds`-registered building (`Building`/Town Hall, `StorageDepot`, `WaterTank`, `Wall`, `BeltSegment`, `Pipe`, `ResearchCenter`, and the 4 stub buildings below) `extends BuildableStructure` (`scripts/core/buildable_structure.gd`), which owns the shared shape: `kind_id: String` (set by `BuildingManager` at placement time, before `add_child`), `upgrade_level: int` + `try_upgrade() -> bool` (spends the current level's cost, in *knowledge*, from `BuildingKinds.get_kind(kind_id).upgrade_costs` — subclasses with an extra effect, like `Building` shaving its spawn-timer interval or `ResearchCenter` boosting its own trickle rate, override and call `super.try_upgrade()` first), `durability`/`max_durability` (currently informational only — nothing damages a building yet, no building-combat mechanic exists), and construction: every instance starts `is_under_construction = true` and non-functional (no spawning/hiring/upgrading/accepting deliveries) until enough blob labor (`add_construction_progress`, driven by blobs in `ConstructState` — any blob kind can contribute, the "Builder" archetype is just the specialist) reaches `BuildingKinds.get_kind(kind_id).build_labor` seconds' worth; a `_construction_meshes()` Template Method hook lets each subclass's own mesh(es) visually rise from a low foundation as progress advances — **must return every visible mesh**, including decorative ones like a port marker, or a piece left out renders at full size from the moment the structure is placed (hit `StorageDepot`/`WaterTank` once, before their port markers were added to the override). `BuildingMenu` is the single, generalized modal for all of them: `open_menu(building)` shows a construction-progress readout while unfinished, or (once built) a "This Building" section (name/durability/ports/upgrade level+perk, all populated via duck-typed field checks so a kind missing a field just hides that row) plus *additionally* the account-wide Global Upgrades/Hire sections only if the clicked building `has_method("hire_blob")` — i.e. only for the Town Hall, since those concepts don't apply to e.g. a Storage Depot. Unlocking new building kinds is its own panel now, not a BuildingMenu section — see `TechTreePanel` under "UI" below.

**Stub buildings** (`scripts/buildings/simple_building.gd`) — Patch of Vegetables, School, Tavern, House. Placeable/constructible/upgradable like any other `BuildingKinds` entry, but with no functional behavior of their own yet (see feature backlog below), so all 4 share the exact same script rather than each hand-rolling an identical `_ready()`/`_construction_meshes()` pair: it collects every direct `MeshInstance3D` child automatically (caching each one's original `position` once in `_ready()`, *not* re-reading it live inside `_construction_meshes()` — `_apply_construction_visual` overwrites a mesh's `position.y` every time construction progresses, so re-deriving "base position" from the mesh's own current position on a later call would re-base off an already-shrunk value and compound toward zero instead of rising correctly, the same footgun `WaterTank`/`Wall` avoid via a cached `@onready var ..._base_position`). The only thing that differs between two stub buildings is their own scene's mesh shape/color and `BuildingKinds` entry (all 4 require `town_hall`, all leave `input_ports`/`output_ports`/`upgrade_costs`/`upgrade_perks` empty rather than describing effects/connections that don't exist yet). `ResearchCenter` (`scripts/buildings/research_center.gd`) started out on this same shared script too, until the tech tree needed a "knowledge" source to spend on itself and the other 4 stubs' unlock costs -- it graduated to its own script (a `KnowledgeTimer` mirroring `Building`'s free-blob-spawn timer, boosted by its own `upgrade_level`) rather than staying generic, the same way any stub building would if given real behavior later.

`LinkableBuilding` (`scripts/core/linkable_building.gd`, `extends BuildableStructure`) is the base for tech-tree buildings that also visually/functionally merge with matching neighbors along the factory grid — `Wall`, `BeltSegment`, `Pipe` (`scripts/factory/pipe.gd`, a water-infrastructure counterpart gated behind `water_tank` rather than seeded unlocked like Wall/Belt, since it has no reason to exist before there's water infrastructure to connect; visually a low horizontal joint+segment rather than a waist-high post+bar, but otherwise a straight copy of Wall's shape — same `_construction_meshes()`/`_links_to`/`_set_connector_visible` trio, `_links_to` narrowed to `neighbor is Pipe`), and `Road` (`scripts/factory/road.gd`, seeded unlocked like Wall/Belt — see feature backlog 2: speeds up any `Blob` crossing a finished one, `blocks_movement` overridden `false` like `BeltSegment`'s for the same reason: a road exists to be walked *on*, and leaving the `true` default would make `PathingManager` treat it as a solid obstacle, routing blobs around the very thing meant to speed them up; its root `StaticBody3D` also needs `collision_layer = 0` + a separate `ClickArea`, the exact same reason `BeltSegment`'s does — being walkable isn't just "not routed around" at the pathing-grid level, it also has to not physically collide via Jolt, which any structure on the normal physics layer would). It holds:

- **`refresh_connections()`** — the 4-neighbor scan (via `GridDirections.CARDINAL_OFFSETS` + `World.get_structure_at`), driven by two Template Method hooks each subclass fills in: `_links_to(neighbor)` (does this neighbor count as "connected" — default is "any non-null neighbor", `BeltSegment`'s behavior as-is; `Wall` overrides to `neighbor is Wall` specifically, so a fence doesn't visually merge into an unrelated belt) and `_set_connector_visible(key, is_visible)` (how "open toward this side" actually looks — `Wall` shows/hides a connector bar per *world-space* cardinal key; `BeltSegment` remaps to its own *rotated local* key first, since a belt's local -Z is always its authored "forward" regardless of which world direction `facing` actually points).
- **`blocks_movement: bool`** (default `true`) — lets `PathingManager` ask "should this cell be solid" without a type check; `BeltSegment` overrides it `false` so blobs walk over a belt instead of routing around it.
- **`_resolve_fair_input(from_direction, slot_free) -> bool`** — a fairness gate for structures that accept input from more than one side (`BeltSegment` today; `Pipe` doesn't use it yet since it has no `try_receive_input` at all — see "logic not required yet" in the feature backlog below). Fixes a real bug: Godot processes scene children in a fixed, deterministic order, so when two senders both feed one shared single-slot receiver, whichever comes first in that order would otherwise win *every* time the slot frees, permanently starving the other (this is what looked like "only one of two conveyor belts merges into a perpendicular one" — not a direction-rejection bug, since `try_receive_input` never gated on `from_direction` at all). The fix remembers the most recently *rejected* sender direction and gives it first refusal the next time the slot opens, with a short timeout (`FAIR_INPUT_GRACE_MSEC`) so a sender that stops trying altogether can't deadlock the slot. Verified with a direct headless test: two senders alternating attempts into one receiver land a near-perfect 50/50 split instead of one getting 40/40 and the other 0/40.

`Wall` and `BeltSegment` (both `scripts/factory/`) migrated onto `LinkableBuilding` from being standalone, always-available, no-construction-delay pieces — they're tech-tree `BuildingKinds` entries now (real unlock state + blob construction labor), but `GameManager.unlocked_buildings` seeds both `true` at game start (alongside `town_hall`) so early-game play is unaffected. `Wall`'s `CollisionShape3D` **must span the full grid cell**, not just its small visual "Post" mesh — it used to be post-sized, leaving a real gap between two adjacent wall cells' actual colliders even though the connector-bar meshes visually bridged them into what looked like one continuous fence; blobs never noticed (they route around the whole reserved cell via the pathing grid, never testing the physical collider), but `Enemy` has no pathing and walks straight at its target, which is what let it pass straight through until this was fixed. `BeltSegment`'s root is now a `StaticBody3D` (inherited from `BuildableStructure`) with `collision_layer = 0` set in `belt_segment.tscn` — **required, not incidental**: every other `LinkableBuilding`/building sits on physics layer 3 (Resources), which `Blob`/`Enemy`'s `collision_mask` includes, and a belt must stay a zero-footprint structure blobs walk straight over rather than collide with; it's still clickable via its existing `ClickArea` (a non-physics `Area3D` child, unchanged) rather than the body itself.

### Factory automation (`scripts/factory/`, grid-based)

`Extractor` (auto-harvests a linked resource node), `Processor` (fixed recipe: 2 wood → 1 plank), and `WaterExtractor` (placeable only on water — see below) are the only remaining always-available, non-`BuildingKinds` grid pieces (costed via `BuildingManager.BUILD_COSTS`, no tech-tree gating, no construction delay) — `Wall`/`BeltSegment`/`Pipe` joined the tech tree, see "Building system" above. Every structure registers onto `BuildingManager`'s grid via `register_structure`, and hands items to its neighbor by calling `get_structure_at(my_cell + facing)` and checking `has_method("try_receive_input")` — the tech-tree buildings (`StorageDepot`/`WaterTank`) do the same on their own input/output ports. `BeltSegment._try_advance_item` holds its item at the front edge (never destroying or auto-collecting it) whenever the next cell is empty or won't accept it right now — a belt line only ever delivers by actually reaching a building that wants it (see feature backlog 2: "resources should be stuck, not destroyed"; `Processor`'s own output still auto-collects to the stockpile when unlinked, a deliberate, not-yet-requested divergence — the backlog item named belts specifically). Placement goes through `BuildingManager`'s build-mode ghost preview (`is_placement_valid` gates cost/occupancy/unlock/fog-of-war/water/kind-specific checks) before anything is actually instantiated, tinting the ghost green/red live; demolishing is a **right-click** in build mode (not a selectable palette kind), refunding half cost.

`WaterExtractor` (`scripts/factory/water_extractor.gd`) is currently a placement-only stub (see feature backlog below) — no `facing`, no output/harvest logic, just a body mesh and group membership. What it *does* implement is the build-mode UX its backlog entry called for: `is_placement_valid` restricts it to `Biomes.is_water_at` tiles the way `Extractor` is restricted to standing near a resource node, and `BuildingManager._refresh_water_extractor_indicators` mirrors `_show_extractor_range_indicators`' "show legal spots" idea — necessarily adapted, though, since water is continuous terrain with no per-instance node to anchor a disc to: rather than one indicator per resource node shown for the whole loaded world (cheap, since resource nodes are sparse), this re-samples a small grid of cells (`WATER_EXTRACTOR_PREVIEW_RADIUS_CELLS`) around the build-mode cursor every time it moves, which only stays cheap by staying local instead of world-wide.

**Build-mode port arrows** (`BuildingManager._refresh_port_indicators`, called on every ghost move/rotate/kind-switch) — a small translucent arrow at each of a kind's input (blue) and output (orange) port cells, colors deliberately matching the ones already used on a *finished* instance (`WaterTank`'s blue `InputMarker`, `Extractor`'s orange `OutputMarker`) so the build-mode preview and the real thing read as the same visual language. Only shown for kinds with an unambiguous, fixed port layout: `BuildingKinds` entries with non-empty `input_ports`/`output_ports` (Town Hall/StorageDepot/WaterTank), plus `Extractor` (output-only, at `facing`) and `Processor` (input opposite `facing`, output at `facing`) since both have exactly one direction each. Deliberately **not** shown for `Belt` — its fair multi-side input (`LinkableBuilding._resolve_fair_input`) means there's no single "the input side" to draw an arrow at, and a misleading one would be worse than none — nor for `Wall`/`Pipe`, which have no ports at all. The arrows are world-space nodes parented directly to `_world`, not to `_build_ghost`, specifically because `_build_ghost` itself still gets rotated by the (for non-rotating kinds, functionally unused) `_build_facing` — a port arrow parented to it would incorrectly inherit that rotation even though `BuildingKinds` ports are always fixed world-relative offsets.

**Build-mode drag-place** (`BuildingManager.DRAG_PLACE_KINDS`/`_try_drag_place`) — holding the left mouse button down while placing `wall`/`belt`/`pipe` (the `LinkableBuilding` kinds, an explicit short list rather than a derived type check, since checking would mean instantiating the scene just to ask) keeps placing into every newly-entered cell as the ghost moves, instead of one click per cell. `Belt` additionally re-faces each new segment toward whichever direction was just traveled from the last-placed cell (`_build_facing` derived from the cell delta, re-applied to the ghost's rotation and to `_refresh_port_indicators` the same way `_rotate_ghost` does) *before* placing it — so a single drag naturally lays a bent belt line that curves to follow the mouse path, corners included, rather than a straight run in whatever direction was picked before the drag started.

Belts and walls both use the same "neighbor-merge" visual trick (`LinkableBuilding.refresh_connections()`, called by `BuildingManager.refresh_neighbor_visuals` on the structure itself plus its 4 neighbors, both when something is placed *and* when it's demolished): hide a side wall/rail wherever an adjacent structure exists, so a chain reads as continuous rather than a row of separate boxed tiles — including through a 90° belt turn, where the "open" sides are whichever two edges actually have neighbors rather than always front/back. Both read the same shared `GridDirections.CARDINAL_OFFSETS` constant (`scripts/core/grid_directions.gd`) rather than each declaring their own copy.

### Gathering tools: weapon/bucket-gated resources (`Blob.equipped_item`)

Every resource type except food (Animals) and water (ponds/lakes) is harvestable by any blob. Food and water instead require the harvesting blob to be carrying the matching tool — `Blob.equipped_item` is `""`/`"weapon"`/`"bucket"`, checked in `OrderManager._issue_harvest_orders` against `ITEM_REQUIRED_FOR_RESOURCE` before an order is even issued (a blob missing the right tool is left alone with floating feedback, not silently skipped). `OrderManager.order_equip` (driven by `UnitInfoPanel`'s Equip Weapon/Equip Bucket buttons) spends wood per blob actually equipped and calls `Blob.try_equip()`. There is no hunger/thirst decay — this is a one-time gate on *who* can collect a resource, not a recurring cost.

### Ores and the Foundry (`scripts/buildings/foundry.gd`, `scripts/world_objects/*_ore.gd` via the shared `ResourceNode` script)

5 ore resource types (`iron`/`gold`/`silver`/`platinum`/`slopium` — the last one a joke resource fitting the project's "AI slop" theme, not a real metal), one per resource-node scene, distributed one each across 5 of the 7 biomes (plains/iron, desert/gold, tundra/silver, volcanic/platinum, swamp/slopium — forest and jungle keep just wood/mushroom, no ore of their own) alongside that biome's existing resources in `Biomes._ready()`. Each is a plain `ResourceNode` scene (same script every other harvestable uses) with its own mesh: a shared grey rock body plus small colored nugget/vein accent meshes, the same two-tone "dark body + colored accent" look `ObsidianShard` already established — except Slopium, which skips the rock body entirely for a squashed, glowing green-and-purple goop blob instead.

`Foundry` (a `BuildingKinds` entry, single input/output port like `WaterTank`, gated behind `research_center` rather than `town_hall` directly — see "Costs and the economy" below, the one deliberate depth added past every other building's flat "just requires Town Hall" tier) smelts any *one* of the 5 ores into its matching bar (`ORE_TO_BAR`, e.g. `iron` → `iron_bar`) — deliberately one generalized building rather than 5 near-identical single-recipe `Processor`s, since nothing asked for a recipe-selection UI. Its single buffer locks to whichever ore type arrives first (`_buffered_type`) and refuses a *different* ore until the batch fully clears back to empty; `ORE_PER_BATCH` (3) of the locked ore smelts into 1 bar over `_effective_process_time()` (`PROCESS_TIME`, shortened 20% per upgrade level up to 2 — computed on demand from `upgrade_level` rather than needing a `try_upgrade()` override, since there's no extra state involved, just a number to recompute). Falls back to `GameManager.add_resource` when its output cell is empty, the same "end of the line" convenience `Processor`'s own output still uses (unlike `BeltSegment`, not touched by the "stuck, not destroyed" change above, since that backlog item named belts specifically). `Effects.resource_color` maps both an ore and its bar to the same display color, so a bar reads as "the refined version of that ore" in floating text/`StorageDepot`'s discovery ledger without needing a second color table.

### Costs and the economy

Three genuinely separate currencies, kept intentionally distinct rather than collapsed into one: **wood/stone/planks/ores+bars** (gathered, spent on `build_cost` placing an individual instance — see `BuildingManager.get_build_cost`/`get_build_cost_resource`), **knowledge** (produced only by `ResearchCenter`, spent on `unlock_cost`/`upgrade_costs` — permanent tech-tree progress, not a per-instance cost), and **blob labor** (`build_labor`, spent in blob-seconds via `ConstructState`, not a stockpile resource at all). A building's `build_cost` and its `unlock_cost` therefore answer different questions — "can I afford one of these right now" vs. "have I researched this tier at all" — which is why `Foundry` costing more `build_cost` than `WaterTank` but requiring the *same* prerequisite (`town_hall`) was a real inconsistency worth fixing (see below), while a *cheaper* `build_cost` next to a *pricier* `unlock_cost` (e.g. `Builder`'s wood hire cost is lower than `Brute`'s despite unlocking later in the chain) isn't a bug — it reflects `Builder`'s lower raw combat/harvest stats, a completely different axis than how deep its `requires` chain sits.

Stone and planks had a real gap before this pass: every resource type in the game gets *gathered* somewhere, but nothing ever *spent* stone or planks — a dead end, not a deliberate design. Rather than touching every building's currency in one sweep (a much bigger, riskier change for a general "make it feel right" pass with no playtesting data to calibrate against), `Wall` specifically was switched to spend stone instead of wood (`BuildingKinds.Kind.build_cost_resource`, defaulting to `"wood"` for every other kind) — its own scene material was already named/colored as stone, making it the one clearly-justified case rather than an arbitrary pick. Planks remains a known, documented gap for a future session rather than something silently left broken.

`Foundry` was also moved from requiring `town_hall` (like every other non-`LinkableBuilding`) to requiring `research_center` instead, and its `unlock_cost` raised alongside that — the only building given real *depth* in the tech tree past the otherwise uniformly flat "everything just needs Town Hall" shape (`Pipe`, a `LinkableBuilding`, already had similar depth via `water_tank`). Ores/smelting are a whole new resource tier layered on top of the original economy; gating them behind the research building the same tier's other new content (`Tech Tree`/knowledge) already depends on reads as more coherent progression than making a 5-recipe smelter available on day one alongside `StorageDepot`.

### Physics layers (`project.godot [layer_names]`)

A project-wide convention, not just a `world.gd`/manager detail: layer 1 = Ground, 2 = Blobs, 3 = Resources (also used for buildings and factory structures — anything solid blobs should path around, distinguished by group membership rather than layer), 4 = Enemies. Raycasts and `collision_mask`s throughout the project assume these bit values. **`BeltSegment` is the one deliberate exception** — its `StaticBody3D` root sits on layer 0 (no layer at all) rather than layer 3, specifically so it has zero physical footprint (see "Building system" above); it stays clickable only via its separate `ClickArea` `Area3D`, which *does* sit on layer 3.

## Code style and design patterns

These are requirements for any new code, not just descriptive notes — refactors and new features should actively look for a fit with one of these before introducing something new.

### GDScript style

- **Prefer `class_name` for anything reused across more than one file.** A `RefCounted`-based stateless helper (see "Shared helpers vs. inheritance" below) still gets a `class_name` even though it's never instantiated meaningfully — that's what makes it callable as `HelperName.some_static_func(...)` from anywhere without a `preload()`.
- **Explicit type annotations over `:=` wherever the right-hand side's type can't be statically resolved.** This bites in two distinct ways, both real bugs hit in this codebase, not hypothetical: (1) a method that exists on a concrete subclass but not on a parameter's declared static type (e.g. `BlobState.physics_update(blob: CharacterBody3D, ...)` calling `blob._find_nearest_enemy_in_range(...)`, a `Blob`-only method); (2) a *global* function whose static return type is looser than it looks — GDScript's generic `max()`/`min()` return an untyped value, so `var new_phase := phase + delta * ... * max(a, b)` fails to infer even though every individual operand is a typed `float` (hit while extracting `LimbAnimator`; fixed with `var new_phase: float = ...`). When in doubt, annotate explicitly rather than assuming `:=` will work.
- **Duck-typing (`"field" in node`, `has_method(...)`) is for genuinely optional, cross-cutting UI concerns** — e.g. `BuildingMenu` populating whichever of durability/ports/upgrade-level/`get_info_text()` a clicked object happens to expose, since a `Wall` and a `BeltSegment` and a `Building` are not "the same kind of thing" and forcing them under one interface just for a UI panel would be backwards. **Real inheritance (`extends`) is for anything that actually *is* the same kind of thing with the same required shape** — this is exactly the distinction this project's own refactor history got wrong at first and then corrected: `Building`/`StorageDepot`/`WaterTank` are all genuinely "a `BuildableStructure`" (same required fields, same construction lifecycle), so they extend a real base class; `Wall`/`BeltSegment`/`Extractor`/`Processor` are not all "the same kind of thing" as each other or as a building, so they stay duck-typed against `BuildingMenu` instead of being forced into a shared type they don't really share.
- **A small stateless helper (static functions on a `RefCounted`) beats copy-pasting math into two unrelated classes that don't otherwise share a type.** Don't reach for inheritance just to deduplicate a formula between two classes that aren't conceptually the same thing (`Blob` and `Enemy` share limb-swing *math*, not identity) — see "Shared helpers vs. inheritance" below.

### Design patterns in active use (name these in comments when extending them)

- **Registry** — `BlobKinds`/`EnemyKinds`/`BuildingKinds`, all `extends Registry` (`scripts/core/registry.gd`): a `_kinds`/`_ordered_ids` catalog with `_register()`/`get_kind()`/`get_ordered_ids()`. Adding a new kind to any of them is a single `_register(Kind.new(...))` call in that registry's own `_ready()` — no UI code changes, since every UI section that lists kinds (hire rows, build palette buttons, unlock rows) is generated from `get_ordered_ids()`.
- **Template Method** — `BuildableStructure._apply_construction_visual()` drives the construction-rising animation generically, calling the `_construction_meshes()` hook each subclass overrides to say *which* mesh(es) participate; `Combatant._show_damage_feedback()` is the same shape for hit-taken feedback (Blob's alarming red flash vs. Enemy/Combatant's neutral default).
- **State** — `BlobState` and its subclasses in `scripts/units/blob/states/` (see "Blob: State pattern" above).
- **Factory** — `Effects`, the sole place that instantiates every transient VFX/SFX object (see "Autoload singletons" above).
- **Shared helpers vs. inheritance** — when two classes need the *same behavior* but aren't the *same kind of thing* (Blob and Enemy don't share a meaningful "is-a" relationship beyond both being a `Combatant`, but both need the same limb-swing math), the fix is a stateless helper of static functions (`LimbAnimator`, `PanelAutofit`, `GridDirections`, `MaterialUtil` in `scripts/core/`), not a forced common ancestor. Each caller keeps its own state (phase accumulators, timers, node references) and just calls the shared function with it; only the *math itself* is deduplicated.

## Load-bearing conventions and gotchas

- **Set `@export` properties before `add_child()`.** Every dynamically-spawned scene (`Blob.kind_id`, `Enemy.kind_id`, `CommandMarker.color`, `ImpactParticles.particle_color`, `ResourceItem.resource_type`, factory structures' `facing`/`kind_id`) reads its exported properties inside `_ready()`, which runs synchronously the moment the node enters the tree. Setting a property *after* `add_child()` is a real bug, not just bad style.
- **Never scale a dynamic physics body (`CharacterBody3D`) itself.** A pop-in/pop-out animation or per-kind size variance must target a purely-cosmetic child node — `Blob.visuals` and `Enemy._visuals` both exist specifically for this (`Enemy` originally scaled its own root before this was corrected; the fix was adding a `Visuals` wrapper matching `Blob`'s pattern). Scaling the body directly produces a degenerate transform Jolt cannot simulate and can permanently corrupt it. (Scaling a `StaticBody3D`'s own root — as `ResourceNode` does for its deplete/respawn animation — is fine; it isn't actively simulated the same way.)
- **Don't trust `velocity` after `move_and_slide()` to reflect real progress.** In this project's Jolt setup it can stay pinned at the input value even when a body is fully blocked. `Blob`'s stall-detector (`_update_stall_detection`) instead samples actual position displacement over a rolling window and kicks off a sideways detour (escalating distance/duration on repeated failure) if it isn't moving. This is a *local* fallback, distinct from (and complementary to) the A*-grid pathing layer — pathing routes around known static obstacles ahead of time, the stall-detector handles whatever it still manages to get stuck on (another moving body, an obstacle type not registered in the pathing grid, etc).
- **`add_child()` on a still-constructing parent fails.** Anything spawning children of `World` from within another node's own `_ready()` must use `call_deferred`, since `World` may still be instantiating its own children at that point.
- **Ground is deliberately absent from Blob/Enemy collision masks**, and `global_position.y` is force-clamped to `0.0` every physics frame for both — this project has no vertical gameplay. `Chunk`'s per-vertex terrain-height noise is purely cosmetic for exactly this reason: it displaces the *visual* ground mesh only, while the ground's own collision body (used for raycasting) stays a flat box, so every click-to-move/grid-placement raycast is unaffected by the bumps.
- **A freshly-created `PrimitiveMesh` applying a `surface_material_override` the same frame it's instantiated can trigger a real (reproduces outside headless too) "Parameter material is null" rendering-server error.** Fix used throughout: duplicate the mesh resource itself and set its `material` property directly (see `ResourceItem._ready()`) instead of overriding a surface on a shared mesh.
- **Right-click harvest orders spread a squad across up to `MAX_BLOBS_PER_NODE` nearby same-type resource nodes** (see `OrderManager._issue_harvest_orders`), each with a deterministic, evenly-spaced approach angle rather than a random one — a deliberate fix for blobs jamming each other when several were sent to the same tree. `Animal` (a wandering food source, `class_name Animal extends ResourceNode`) deliberately keeps its own wander radius small for the same reason: the approach-point math assumes a resource node is roughly stationary.
- **WASD panning and Q/E rotation both use *physical* key codes** (`Input.is_physical_key_pressed`, not the localized keycode) so the same binding reads correctly as "WASD to pan, Q/E to rotate" on QWERTY and "ZQSD to pan, A/E to rotate" on AZERTY without any layout-specific branching — physical `KEY_W`/`KEY_A`/`KEY_Q` are the keys labeled Z/Q/A respectively on an AZERTY keyboard, and E is unchanged between the two layouts.
- **GDScript type inference (`:=`) fails on values returned through an untyped/duck-typed path, or through a looser-than-expected global function.** See "Code style and design patterns" above for both concrete forms this has taken (a `Blob`-only method called through a param typed as the parent `CharacterBody3D`; a fresh `:=` declaration whose expression includes `max()`/`min()`) — this has come up repeatedly across `scripts/units/blob/states/`, `world.gd`, `building_menu.gd`, `scripts/core/limb_animator.gd`, and now every manager under `scripts/world/managers/` that calls back into `_world` (see "world.gd and its managers" above).
- **A minimap/UI `Control` meant to receive clicks needs `mouse_filter = 0` (STOP), not the default `MOUSE_FILTER_IGNORE`.** `Minimap`'s `Display` control was originally click-through (a pure read-only overview); adding click-to-move-camera required switching its `mouse_filter` before `_gui_input` would ever fire.
