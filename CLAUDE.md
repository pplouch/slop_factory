# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Godot 4.7 (GDScript) 3D top-down idle/incremental "RTS-lite" game — working title "Rogue idle slop factory survivor rpg ultimate" (theme: "ai slop generation to get sloppier," played for laughs). A single scene (`world.tscn`) streams in a Minecraft-style chunked map across three biomes, spawns "blob" worker units the player commands with RTS-style click/drag selection plus standing orders (patrol/hold/explore), gathers resources into a shared stockpile, and layers on a tech-tree of upgradable buildings, hireable unit archetypes, biome-specific enemies, a grid-based factory-automation subsystem (extractors/belts/processors/walls) with A*-grid pathing, and a colony-wide food/water upkeep system.

## Running and validating

There is no test suite (GUT/gdUnit are not installed) and no build step — GDScript runs directly. Godot's own CLI is the only validation tool available, and is the primary way to catch mistakes without opening the editor:

- **Import/parse check** (catches script syntax errors, bad `class_name`/autoload registration, broken resource references):
  `<godot> --headless --path . --import --quit`
- **Headless runtime smoke test** (actually runs `_ready`/`_process`/`_physics_process` for N frames and prints runtime errors):
  `<godot> --headless --path . res://world.tscn --quit-after <N>`
  - Add `--fixed-fps 60` to decouple simulated time from wall-clock time, so e.g. a 60-second building-spawn timer or a 45-second resource-respawn timer can be exercised in a couple of real seconds.
- Some bugs (material/shader errors) only reproduce under a real graphics driver, not the headless dummy renderer — when in doubt, also run once **without** `--headless` (it won't exit on its own; kill the process after a few seconds). For anything purely visual (mesh/material/lighting/UI layout), a headless smoke test proves it doesn't *crash*, not that it *looks right* — launch the real renderer and capture a screenshot (on Windows: PowerShell `Start-Process` + `System.Windows.Forms.Screen`/`System.Drawing.Graphics.CopyFromScreen`, since no other screenshot tool is available) to actually confirm the visual before calling it done.
  - Godot's GL Compatibility renderer can produce visual quirks that never show up in a diagnostic print of transform/scale/rotation data (all correct) yet look wrong on screen — e.g. a wide, thin, flat-ish mesh (like a peaked roof) viewed from this project's steep default camera angle can look like a huge misshapen wedge purely from perspective foreshortening. Before treating an odd-looking render as a code bug, check whether it's reproducible/position-dependent (print the object's actual transform, compare against a second instance at a different position in the same screenshot) rather than assuming the geometry or mesh-generation code is wrong.
- There's no way to simulate mouse/keyboard input headlessly. To validate anything mouse-driven (selection, build-mode placement) or keyboard-driven (standing-order shortcuts), call the underlying `world.gd`/`Blob` methods directly (e.g. `_try_place_structure()`, `_issue_harvest_orders()`, `command_patrol(...)`) rather than synthesizing `InputEvent`s — except physical keyboard state specifically, which *can* be faked headlessly via `Input.parse_input_event(InputEventKey...)` with `physical_keycode` set, letting `Input.is_physical_key_pressed()` (what `camera_rig.gd` and `world.gd`'s order-key handling both read) see it.
- Typical validation loop: temporarily wire a `_debug_test_hook()` (or similar) into `world.gd`'s `_ready()` (via `.call_deferred()` if it needs to `await` a few frames), run headless, read the printed output, then remove the debug code before finishing. Never leave `_debug_*` methods or stray `print("TEST ...")` calls in a finished changeset.
- On this machine the Godot 4.7.1 binary is a portable install at `~/Downloads/Godot_v4.7.1-stable_win64.exe/Godot_v4.7.1-stable_win64_console.exe` — note it unpacked into a directory with the same name as the zip, so the real executables are one level inside, not the top-level path itself.

## Architecture

### Autoload singletons (`res://scripts/autoload/*.gd`, registered in `project.godot [autoload]`)

- **`GameManager`** — sole source of truth for the resource stockpile (`wood`/`stone`/`planks`/`mushroom`/`cactus_fiber`/`food`/`water`, arbitrary string keys), the 5 account-wide building upgrades (`speed`/`strength`/`efficiency`/`capacity`/`growth`), the building tech-tree unlock state (`unlocked_buildings`), and colony food/water upkeep. All spending goes through `try_purchase_upgrade`/`try_spend_wood`/`try_unlock_building`; nothing else mutates `resources`/`upgrade_levels`/`unlocked_buildings` directly. Emits `resource_changed`/`upgrade_changed`/`building_unlocked`/`colony_supply_changed` — HUD, BuildingMenu, BuildPalette, and every Blob react to these instead of polling. `consume_colony_supplies(blob_count)` (called periodically by `world.gd`, which owns the population query) drains food/water and, if either runs out, applies a speed/harvest penalty to every Blob via `get_starvation_speed_multiplier()`/`get_starvation_harvest_multiplier()` until resupplied.
- **`Effects`** — factory for every transient VFX/SFX object (floating damage/pickup text, particle bursts, order-confirmation rings, conveyor `ResourceItem`s, procedurally-synthesized "cute chirp" sounds) plus the one place that maps a resource type to a display color. Gameplay scripts never instantiate these scenes directly. The chirp waveform (`play_chirp`) is raw 16-bit PCM built once in `_ready()` and reused across every play with a randomized `pitch_scale` — no audio asset files exist in this project.
- **`BlobKinds`** — data-driven registry of the four hireable unit archetypes (worker/scout/hauler/brute) and their stat multipliers/hire cost/look. Adding a kind is one call in `blob_kinds.gd`'s `_ready()`; BuildingMenu's hire rows are generated from `get_ordered_ids()`, so nothing else needs to change.
- **`EnemyKinds`** — the same Registry pattern applied to hostile creatures (slime/wolf/spider/scorpion/bandit): one `Enemy` scene/script, `kind_id` selects health/attack/speed multipliers and look. Mirrors `BlobKinds` exactly.
- **`BuildingKinds`** — registry of placeable building types (currently `town_hall`, `storage_depot`). Each `Kind` carries its scene, wood build cost, input/output port *directions* (`Vector2i` offsets from the building's own single anchor cell — see "Building system" below), tech-tree `unlock_cost`/`requires`, `max_durability`, and per-instance `upgrade_costs`/`upgrade_perks` arrays. Adding a new building kind is one `_register` call here plus a scene/script implementing `try_receive_input`/(optionally) `try_upgrade`.
- **`Biomes`** — registry of the three biomes (`plains`/`forest`/`desert`), each with a ground tint, terrain-relief amplitude, resource-node scene list, and `enemy_kind_ids`. `biome_for_world_pos(pos)` is the single source of truth for "what biome is here": an inner `PLAINS_RADIUS` circle around the origin (where founder blobs start and the player builds first), split into a forest half and a desert half beyond that by the sign of `atan2(z, x)` (a north/south split, not east/west, despite the name) — deliberately simple angle/distance rules rather than real noise-based blending, so biome borders stay predictable.

### `world.gd` — the central controller

Owns everything that isn't a self-contained actor: chunk streaming, mouse/keyboard input routing (`_unhandled_input` branches into normal play, or into build-mode input if `_build_mode_active`), unit selection state, the factory-placement grid, and the A*-grid pathing layer.

- **Chunk streaming**: the map is tiled into `Chunk`-sized (`Chunk.CHUNK_SIZE`) squares, keyed by `Vector2i` chunk coordinate in `_loaded_chunks`. `_process` periodically (`CHUNK_CHECK_INTERVAL`, not every frame) calls `_ensure_chunks_loaded(camera_rig.position)`, which generates any chunk within `CHUNK_LOAD_RADIUS` of the camera's current focus point that doesn't exist yet. **Deliberately load-only, never unloaded** — resource nodes and enemies inside an already-generated chunk are live, persistent game state a blob might be en route to; freeing them out from under it would be a real bug, not just a visual pop. `MINIMAP_HALF_SIZE`/`PATHING_GRID_HALF_SIZE` (both 90 as of this writing) are fixed scales for the minimap and pathing grid respectively — **not** kept in sync with `CameraRig.BOUNDS` (currently 2000, tuned independently), so panning far enough eventually outruns pathing-grid/minimap coverage; `compute_path` degrades gracefully (empty array → direct-line fallback) rather than erroring in that case, but this is worth revisiting if the playable area is meant to extend that far in practice.
- **Factory placement grid**: `_grid_structures: Dictionary[Vector2i, Node]`, exposed via `grid_to_world` / `world_to_grid` / `get_structure_at` / `register_structure` so belts/extractors/processors/walls/buildings can look up their neighbors without holding direct references to each other. Every placed structure occupies exactly one cell (a multi-port building's ports are *directions to neighboring cells*, not additional cells it claims — see "Building system").
- **Pathing grid**: a single `AStarGrid2D` (`_pathing_grid`) covering `PATHING_GRID_HALF_SIZE`, sharing `GRID_CELL_SIZE` with the factory grid. Every placed structure except belts (`_kind_blocks_movement`) marks its cell solid via `_mark_pathing_cell`; `compute_path(from, to)` first checks a direct line of sight (`_has_clear_line`, sampled every half-cell) and only falls back to `_pathing_grid.get_id_path(...)` when something's actually in the way — keeps normal unobstructed movement smooth instead of visibly grid-snapped.
- UI panels (`HUD`, `BuildingMenu`, `BuildPalette`, `DebugMenu`, `UnitInfoPanel`, `ResourceInfoPanel`, `Minimap`) are dumb views: they only emit signals (`toggle_requested`, `kind_selected`, etc.) and expose `set_active`/`open_menu`-style setters. `world.gd` owns all the actual logic and wires to their signals in `_ready()`.
- Clicking a building routes through `_find_building_owner(collider)`, which handles two different node shapes: `Building`'s collidable body is a nested `Solid` child (owner = collider's parent), while `StorageDepot`/`Wall` attach their script directly to the root `StaticBody3D` (owner = the collider itself). Checking `is_in_group("buildings")` on *both* the collider and its parent is required — checking only the parent (as an earlier version of this code did) silently never opens the modal for `StorageDepot`/`Wall`.

### Blob: State pattern (`scripts/units/blob/blob.gd` + `scripts/units/blob/states/`)

A Blob's per-frame behavior is delegated to `current_state.physics_update(self, delta)`, where `current_state` is one of `IdleState`/`MovingState`/`HarvestingState`/`ReturningState`/`PatrolState`/`HoldState`/`ExploreState` (each a `RefCounted` with `class_name`, so no preloading is needed). A state's `physics_update` returns the next `BlobState` to transition into, or `null` to stay — that return value is the entire transition mechanism. `blob.gd` itself only holds what's genuinely shared across states (movement stepping, stall-recovery, path-following, inventory, stats); the states hold just the branching logic for their own phase and call back into `blob`'s helper methods.

- **Standing orders**: `command_patrol(point_b)`/`command_hold()`/`command_explore()` transition directly into `PatrolState`/`HoldState`/`ExploreState`, which (unlike the other states) never transition themselves — the only way out is a fresh player order, which naturally overrides them via the same `_transition_to` call every other command already uses. Player-facing: `P` arms "pending patrol" (the *next* right-click sets the far point; `world.gd._pending_patrol`), `H`/`X` take effect immediately using the blob's current position as anchor. `HoldState` deliberately breaks the "a blob never chases" rule (see Combat below) within its own `DETECTION_RADIUS` — that's the point of a sentry order.
- **Idle ambient behavior**: `IdleState` periodically (every few seconds) either takes a couple of steps to a small nearby point or, if another idle blob is close by, turns to face it and chirps — cosmetic "living creature" flavor layered on top of "otherwise stand still," never leaves `IdleState`.
- **Pathfinding integration**: `_set_destination(target)` calls `World.compute_path(...)` and stores the result in `path_queue`; `_advance_along_path()` (called unconditionally every physics frame, alongside `_update_stall_detection`/`_update_combat`) pops waypoints as `move_target` is reached. Every state that steers via `_step_toward(blob.move_target)` therefore follows a routed path automatically without needing to know pathing exists at all.

### Combat: `Combatant` base class (`scripts/core/combatant.gd`)

`Blob` and `Enemy` both `extends Combatant`, which owns health/regen/evasion math, `take_damage()`, and a billboarded two-quad health bar built in code (`_build_health_bar`) and shown at each combatant's feet. The health bar's materials need **both** `cull_mode = CULL_DISABLED` (a billboard-transformed quad's front face isn't reliably toward the camera) **and** `no_depth_test = true` (sitting this low, the unit's own body constantly occludes it depth-wise from this project's top-down camera) — either alone leaves it invisible in practice, not just dim. Damage feedback is a template method (`_show_damage_feedback`): Combatant's default is a neutral/rewarding look, used as-is by `Enemy` (the player hurting an enemy is good news); `Blob` overrides it with a more alarming red flash, since a blob taking damage is bad news. Combat is reactive, not proactive — a Blob keeps doing its job and only fights back if an enemy comes within its own short attack range; it never chases (except while under a `HoldState` sentry order, see above).

### Building system: `BuildingKinds`, per-instance upgrades, generic info modal

Any building (`Building`/`Town Hall`, `StorageDepot`, and eventually more) exposes the same duck-typed shape: `kind_id: String` (set by `world.gd` at placement time, before `add_child`), `upgrade_level: int` + `try_upgrade() -> bool` (spends the current level's cost from `BuildingKinds.get_kind(kind_id).upgrade_costs`, applying its own numeric effect — e.g. `Building` shaves its spawn-timer interval, `StorageDepot` grows its buffer capacity), and `durability`/`max_durability` (currently informational only — nothing damages a building yet, no building-combat mechanic exists). `BuildingMenu` is the single, generalized modal for all of them: `open_menu(building)` always shows a "This Building" section (name/durability/ports/upgrade level+perk, all populated via duck-typed field checks so a kind missing a field just hides that row) and *additionally* shows the account-wide Global Upgrades/Hire/Unlock-Buildings sections only if the clicked building `has_method("hire_blob")` — i.e. only for the Town Hall, since those concepts don't apply to e.g. a Storage Depot.

`Wall` (in `scripts/factory/`) is a simpler, non-`BuildingKinds` placeable (like belt/extractor/processor, costed via `world.gd`'s `BUILD_COSTS` dict, no tech-tree gating) that exists purely as a pathing obstacle with a durability stat for the info-modal's sake; it shows a connector bar toward each neighboring cell that also holds a `Wall` (`refresh_connections`, checking `neighbor is Wall` specifically — unlike `BeltSegment`'s equivalent method, which opens toward *any* neighboring structure).

### Factory automation (`scripts/factory/`, grid-based)

`Extractor` (auto-harvests a linked resource node), `BeltSegment` (carries one `ResourceItem` at a time, scrolls a procedural striped floor texture built fresh **per-instance** — sharing one material across every belt would make the scroll speed compound as more belts are placed, since each instance's own `_process` would add to the same `uv1_offset`), `Processor` (fixed recipe: 2 wood → 1 plank), `StorageDepot` (2-in/2-out buffer, demonstrates the full port range), and `Wall` all register onto `world.gd`'s grid via `register_structure`, and hand items to each other by calling `get_structure_at(my_cell + facing)` and checking `has_method("try_receive_input")`. A belt (or processor output) with nothing in the next cell auto-delivers straight to `GameManager`'s stockpile — that "end of the line" rule means a conveyor chain never needs to visibly terminate at a building. Placement goes through `world.gd`'s build-mode ghost preview (`_is_placement_valid` gates cost/occupancy/extractor-must-be-near-a-resource-node/unlock checks) before anything is actually instantiated; demolishing is a **right-click** in build mode (not a selectable palette kind), refunding half cost.

Belts and walls both use the same "neighbor-merge" visual trick (`refresh_connections`, called by `world.gd._refresh_neighbor_visuals` on the structure itself plus its 4 neighbors, both when something is placed *and* when it's demolished): hide a side wall/rail wherever an adjacent structure exists, so a chain reads as continuous rather than a row of separate boxed tiles — including through a 90° belt turn, where the "open" sides are whichever two edges actually have neighbors rather than always front/back.

### Physics layers (`project.godot [layer_names]`)

A project-wide convention, not just a `world.gd` detail: layer 1 = Ground, 2 = Blobs, 3 = Resources (also used for buildings and factory structures — anything solid blobs should path around, distinguished by group membership rather than layer), 4 = Enemies. Raycasts and `collision_mask`s throughout the project assume these bit values.

## Load-bearing conventions and gotchas

- **Set `@export` properties before `add_child()`.** Every dynamically-spawned scene (`Blob.kind_id`, `Enemy.kind_id`, `CommandMarker.color`, `ImpactParticles.particle_color`, `ResourceItem.resource_type`, factory structures' `facing`/`kind_id`) reads its exported properties inside `_ready()`, which runs synchronously the moment the node enters the tree. Setting a property *after* `add_child()` is a real bug, not just bad style.
- **Never scale a dynamic physics body (`CharacterBody3D`) itself.** A pop-in/pop-out animation or per-kind size variance must target a purely-cosmetic child node — `Blob.visuals` and `Enemy._visuals` both exist specifically for this (`Enemy` originally scaled its own root before this was corrected; the fix was adding a `Visuals` wrapper matching `Blob`'s pattern). Scaling the body directly produces a degenerate transform Jolt cannot simulate and can permanently corrupt it. (Scaling a `StaticBody3D`'s own root — as `ResourceNode` does for its deplete/respawn animation — is fine; it isn't actively simulated the same way.)
- **Don't trust `velocity` after `move_and_slide()` to reflect real progress.** In this project's Jolt setup it can stay pinned at the input value even when a body is fully blocked. `Blob`'s stall-detector (`_update_stall_detection`) instead samples actual position displacement over a rolling window and kicks off a sideways detour (escalating distance/duration on repeated failure) if it isn't moving. This is a *local* fallback, distinct from (and complementary to) the A*-grid pathing layer — pathing routes around known static obstacles ahead of time, the stall-detector handles whatever it still manages to get stuck on (another moving body, an obstacle type not registered in the pathing grid, etc).
- **`add_child()` on a still-constructing parent fails.** Anything spawning children of `World` from within another node's own `_ready()` must use `call_deferred`, since `World` may still be instantiating its own children at that point.
- **Ground is deliberately absent from Blob/Enemy collision masks**, and `global_position.y` is force-clamped to `0.0` every physics frame for both — this project has no vertical gameplay. `Chunk`'s per-vertex terrain-height noise is purely cosmetic for exactly this reason: it displaces the *visual* ground mesh only, while the ground's own collision body (used for raycasting) stays a flat box, so every click-to-move/grid-placement raycast is unaffected by the bumps.
- **A freshly-created `PrimitiveMesh` applying a `surface_material_override` the same frame it's instantiated can trigger a real (reproduces outside headless too) "Parameter material is null" rendering-server error.** Fix used throughout: duplicate the mesh resource itself and set its `material` property directly (see `ResourceItem._ready()`) instead of overriding a surface on a shared mesh.
- **Right-click harvest orders spread a squad across up to `MAX_BLOBS_PER_NODE` nearby same-type resource nodes** (see `World._issue_harvest_orders`), each with a deterministic, evenly-spaced approach angle rather than a random one — a deliberate fix for blobs jamming each other when several were sent to the same tree. `Animal` (a wandering food source, `class_name Animal extends ResourceNode`) deliberately keeps its own wander radius small for the same reason: the approach-point math assumes a resource node is roughly stationary.
- **WASD panning and Q/E rotation both use *physical* key codes** (`Input.is_physical_key_pressed`, not the localized keycode) so the same binding reads correctly as "WASD to pan, Q/E to rotate" on QWERTY and "ZQSD to pan, A/E to rotate" on AZERTY without any layout-specific branching — physical `KEY_W`/`KEY_A`/`KEY_Q` are the keys labeled Z/Q/A respectively on an AZERTY keyboard, and E is unchanged between the two layouts.
- **GDScript type inference (`:=`) fails on values returned through an untyped/duck-typed path** — e.g. a `BlobState.physics_update(blob: CharacterBody3D, ...)` calling `blob._find_nearest_enemy_in_range(...)` (a method that exists on `Blob` specifically, not on the parameter's static `CharacterBody3D` type). Use an explicit type annotation (`var enemy: Node = ...`) instead of `:=` whenever the right-hand side's type can't be statically resolved this way; this has come up repeatedly across `blob_states/`, `world.gd`, and `building_menu.gd`.
