# Feature backlog 3: bug reports (post-backlog-2)

_Historical record for [Rogue idle slop factory survivor rpg ultimate](../../CLAUDE.md) — what landed and why, kept for provenance, not needed for day-to-day work._

## Feature backlog 3 (bug reports, post-backlog-2)

An ongoing set of regressions/UX complaints the player found by actually playing right after backlog 2 landed. Same conventions as before (headless-verified via direct-call debug hook, real-renderer screenshot for the visual claim, committed once verified).

**Done:**
- [x] Resources are not visible anymore on the belts — not a rendering bug, and not fully fixed on the first pass (see below). Root cause, first pass: backlog 2's "belts hold stuck items forever instead of auto-collecting" fix (`BeltSegment._try_advance_item` no longer clearing a full belt into the stockpile) turned each producer's own pre-existing "if the belt rejects delivery, that's a rare race, just reroute/destroy" fallback from a genuine rare edge case into the *common* case for any belt run with no live consumer at the end — so `Extractor` was destroying every harvested item after the first, and `Processor`/`Foundry` were silently bypassing every finished batch straight to the stockpile instead of ever placing it onto the belt. Fixed by adding an `_output_is_free()` pre-check to all three producers, gating harvesting/batch-start on the output belt actually having room. This alone still wasn't enough, and the player correctly reported the belt still showing nothing: `_output_is_free()` only checked the belt's single-item slot, never whether the belt had actually *finished being built* -- every `BeltSegment`, like every `BuildableStructure`, starts `is_under_construction = true` and unconditionally rejects `try_receive_input` until a blob finishes building it (`build_labor` = 6s), so a brand-new extractor+belt pair (the ordinary, common case right after placing both) would harvest immediately, get rejected by the still-unbuilt belt, and destroy/bypass the item every single tick for the whole construction period -- silently draining the resource node the entire time with nothing ever appearing, exactly the reported symptom. The previous debug hook that "verified" the first-pass fix had force-finished the belt's construction before testing (`add_construction_progress(9999.0)`), which is precisely what masked this. Fixed by extending `_output_is_free()` on all three producers to also duck-type `is_under_construction` and treat an unbuilt belt as not-free. Verified via a direct-call debug hook that exercises the real sequence end to end: places an extractor + belt through the actual `BuildingManager.try_place_structure()` path (not hand-set state), confirms the fresh belt starts `is_under_construction = true`, confirms 3 extractor ticks against it drain *zero* resource and leave `current_item` null, then finishes construction and confirms the very next tick correctly drains `EXTRACT_AMOUNT` and produces a valid `ResourceItem` riding the belt.
- [x] War fog covers only a small area, then the map is fully visible beyond it (should extend as far as the player can actually go) — root cause: `FogManager`'s coverage bound and `Minimap`'s own local-overview bound had been unified into one shared `FOG_HALF_SIZE = 90.0` constant back when the two were made to share fog data, but 90 world units is far smaller than `CameraRig.BOUNDS` (2000), the camera's actual pan limit — so a player panning even a moderate distance from spawn would sail straight past tracked coverage into `FogManager.is_revealed`'s "outside tracked coverage = already revealed" fallback (see its own doc comment), reading as fog just stopping partway across the map. Fixed by splitting the shared constant into two independent ones in `world.gd`: `MINIMAP_HALF_SIZE` (90, unchanged, purely a "how much local area does the minimap overview show" number) and `FOG_HALF_SIZE` (2000, matched by hand to `CameraRig.BOUNDS`), with `FogManager.FOG_RESOLUTION` scaled 48→1024 alongside it to keep the same ~3.9 world-units-per-cell granularity rather than going coarse. Since `Minimap` still draws the very same shared `fog_texture` (now representing a 4000-unit-wide area instead of 180), gave it its own `_fog_world_half_size` + `set_fog_source()` and had `_draw()` crop to just the sub-region its own smaller bound actually shows via `draw_texture_rect_region`, rather than stretching the whole enlarged texture across the minimap panel (which would've shrunk the actually-revealed area near the player down to an unreadable speck). Verified via a direct-call debug hook that `FogManager.world_half_size` reads 2000 and a position far outside the old 90-unit bound (`(1500, 0, 1500)`) correctly reads unrevealed before an explicit reveal there and revealed after; confirmed visually with a real-renderer screenshot that the revealed area now renders as an organic blob shape trailing the blobs' actual movement with true black fog beyond it, not a small fixed circle giving way to full visibility.
- [x] When opening a UI box, all others should close and units should be deselected — `BuildingMenu`, `ResourceInfoPanel`, `EnemyInfoPanel` (all backdrop-modal, close automatically on an outside click) and `TechTreePanel`/`DebugMenu` (non-modal always-available corner toggles, no backdrop at all) had never been made mutually exclusive; because `TechTreePanel` is the last CanvasLayer child in `world.tscn` (drawn/hit-tested on top of everything) and `DebugMenu` sits above `BuildingMenu` in the same tree, their always-visible toggle buttons stayed clickable even while another box's backdrop was up, letting boxes stack indefinitely, and unit selection (which has no backdrop either) could sit underneath any of them the whole time. Fixed with a single coordinator, `World.close_other_ui(opened)`, that closes every one of {`building_menu`, `resource_info_panel`, `enemy_info_panel`, `tech_tree_panel`, `debug_menu`} except whichever just opened and clears the current blob selection (which in turn hides `UnitInfoPanel`) -- every close call is already idempotent, so this is safe to call unconditionally rather than needing each call site to track what else is open. Wired at every "a box opened" call site: `SelectionManager.handle_click_select`'s enemy/building/resource-node branches, `SelectionManager.selection_changed()` (unit selection becoming non-empty), a new `TechTreePanel.opened` signal (emitted from `_toggle()`), and `DebugOverlayManager.toggle_debug_menu()`. Verified via a direct-call debug hook: selecting a blob shows `UnitInfoPanel`; opening `TechTreePanel` afterward hides it again and clears the selection; re-selecting the blob then closes `TechTreePanel` back.
- [x] When right-clicking on nothing in build mode, build mode should close — `BuildingManager.handle_build_input`'s right-click handler unconditionally called `demolish_at(_build_ghost_cell)` (itself already a safe no-op on an empty cell), leaving a right-click on empty ground silently doing nothing rather than giving the player an obvious way to back out of build mode short of finding Escape or the palette's own toggle button. Changed to demolish (staying in build mode) only when a structure actually occupies the cell, and exit build mode via the existing `toggle_build_mode()` otherwise -- a bare right-click on nothing now reads as "I'm done here." Verified via a direct-call debug hook: right-clicking a freshly-placed Wall demolishes it and build mode stays active; right-clicking an empty cell right after exits build mode.
- [x] Curbs on a LinkableBuilding should not disappear if the neighbor is a different-kind LinkableBuilding — investigated and did NOT reproduce: `Wall`/`Road`/`Pipe` already override `LinkableBuilding._links_to(neighbor)` with a real type check (`neighbor is Wall`/`is Road`/`is Pipe`), not a generic `neighbor is LinkableBuilding` or a `kind_id` string compare, so a Road next to a Wall already correctly leaves both sides' connector/curb showing an exposed (non-merged) edge -- only a same-kind neighbor (`_links_to` returning true) hides either one. Verified via a direct-call debug hook: placed a Wall directly next to a Road, force-finished both, and confirmed the Wall's connector toward the Road stays hidden (not merged -- Wall's own convention is *connector visible = merged*) while the Road's curb toward the Wall stays visible (exposed edge -- Road's convention is the opposite, *curb visible = NOT merged*); a same-kind Wall-next-to-Wall pair placed alongside it still correctly merges (connector shows), confirming nothing regressed. No code change landed for this item -- the design was already correct from when Road was added (see backlog 2).
- [x] When creating a new building, assign free workers to build it — `BuildingManager.try_place_structure()` now calls a new `_auto_assign_builders(node)` right after placing anything that starts under construction: finds every blob currently in `IdleState`, sorts by distance to the new building, and sends up to `AUTO_ASSIGN_BUILDER_CAP` (2) of the closest via `Blob.command_build()` with evenly-spaced approach angles -- the same trick `OrderManager._issue_build_orders` already uses for a player-issued build order, just auto-triggered and sourced from every idle blob in the world instead of the current selection. Capped rather than grabbing the whole idle workforce for one wall, since a freed-up worker elsewhere will pick this building up later anyway once nothing closer needs it (see the next item's build-queue behavior). A no-op if no blob is currently idle. Verified via a direct-call debug hook: placing a Wall while a founder blob is idle immediately assigns it (`pending_build_target` now points at the new wall) and transitions it into `MovingState`.
- [x] When a worker is assigned to build, it should queue all unfinished buildings and build them afterwards — rather than a literal pre-built queue (which could go stale if other blobs finish/demolish things mid-list), `ConstructState` now calls a new `Blob._next_build_or_idle()` whenever its current target finishes or disappears: this dynamically searches every member of the `"structures"`/`"buildings"` groups (both, since Town Hall is the one kind that only joins `"buildings"`) for the nearest one still under construction and heads there next, only falling back to `IdleState` once genuinely nothing is left unfinished anywhere -- the same "loop back if there's more work, else go idle" shape `Blob._deposit()` already uses for harvesting. Combined with the auto-assign item above, a small number of workers now sweep through every unfinished building in sequence rather than each stopping after just the one job it was originally sent to. Verified via a direct-call debug hook: a blob mid-`ConstructState` whose target gets force-finished correctly retargets a second, still-unfinished Wall placed nearby and re-enters `MovingState`; once every unfinished structure in the scene is force-finished, the same blob correctly falls back to `IdleState` instead of retargeting nothing.
- [x] Buildings should have a visual tip showing they're not finished yet — previously the only cue was the rise-from-ground mesh animation itself (`BuildableStructure._apply_construction_visual`, easy to miss once a building is most of the way up) or opening `BuildingMenu` to read progress as text. Added a small always-visible billboarded progress bar (dark background + gold fill, the same two-quad/billboard/no-depth-test construction `Combatant._build_health_bar` uses for a unit's health, just floating above the structure instead of at its feet) directly to `BuildableStructure`, piggybacking on `_apply_construction_visual`'s existing call sites (`_ready()`, every `add_construction_progress()` tick, and the finishing call) rather than needing every one of its 10 subclasses to call one more setup method -- built lazily the first time it runs, torn down for good once `fraction >= 1.0`. Since `LinkableBuilding` (Wall/Belt/Pipe/Road) already extends `BuildableStructure`, this covers every constructable kind in the game for free, including the grid pieces, with a single change in one file. Verified via a direct-call debug hook: the bar exists immediately after placement, its fill fraction reads exactly 0.5 after adding half the required labor, and it's removed (node freed, reference nulled) the instant construction finishes; confirmed visually in the real client that a freshly-placed Wall shows the bar floating above it.
