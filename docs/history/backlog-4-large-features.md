# Feature backlog 4: large multi-session features

_Historical record for [Rogue idle slop factory survivor rpg ultimate](../../CLAUDE.md) — what landed and why, kept for provenance, not needed for day-to-day work._

## Feature backlog 4 (large, multi-session)

A 24-item list (the player's own 25 asks, with "add a main menu" and "make it the starting scene" tracked as one combined item since they're only meaningfully doable together) -- by far the largest single batch handed over -- spanning quick bug fixes, UI/UX polish, and several substantial new systems (main menu + meta-progression, day/night + weekly wave, villages, chests, Hero unit + XP, mini-games). Given the size, items are being worked in roughly this order: quick self-contained bug fixes and UI polish first, then the two interrelated unit-AI/movement items (task locking, formation movement), then world-generation tuning (biome scale, height removal), then more quick bug fixes, then the large new-content systems last, since those are the most speculative ("wanky dandy fun features" deliberately has no fixed spec yet -- see its own note below) and benefit from everything else being settled first. Logged in full up front (all 24, most still unchecked) rather than only as each is picked up, so scope stays visible across however many sessions this takes; check items off and add implementation notes here as they land, same as every backlog before this one.

- [x] Units still have a problem queuing construction, moving in group, or attributing a task to a group -- they should each pick a task (a building or a resource) and lock it so others pursue whatever's still unlocked instead — root cause: capacity checks for both harvest and build assignment only ever looked at state *local to the current call*. `OrderManager._issue_harvest_orders` tracked its own per-call `assigned_count` dict, so a *second* group order issued later (or an ambient auto-assignment) had no idea a node was already fully worked by an earlier order and would happily stack more than `MAX_BLOBS_PER_NODE` onto it; `Blob._find_nearest_unfinished_structure` (backlog 4's own build-queue item) had no capacity check at all, so several blobs freeing up around the same time would all independently compute "nearest unfinished" and pile onto the exact same one while other unfinished buildings sat completely unworked. Verified via a direct-call debug hook: two *separate* `_issue_harvest_orders` calls targeting the same tree correctly redirect the second call's blob to a different nearby tree once the first is at capacity; auto-assigning builders to a freshly-placed Wall still caps at 2 even with 3 idle blobs available; and a separately-freed idle blob's own `_find_nearest_unfinished_structure()` correctly skips an already-full Wall in favor of a second, still-unworked one.
- [x] When moving a group of units, they should arrange themselves into an organized grid, like a war battalion, rather than all converging on one point — a plain multi-blob move order (right-click empty ground) used to send every selected blob to the exact same point, only papering over the resulting scrum with a "growing move_tolerance" hack so at least one blob wouldn't get stuck circling forever. - [x] Add a day/night cycle; every 7 days, a large enemy wave attacks the Town Hall — new `DayNightManager` (`scripts/world/managers/day_night_manager.gd`), split out like every other manager, owns a single `_elapsed_seconds` clock. `DAY_LENGTH_SECONDS` (300s, i.e. 5 real minutes/day) is an arbitrary pacing choice -- nothing in the backlog specified one -- picked so a single sit-down session sees several day/night transitions and at least one wave, rather than a cycle so slow it never completes or so fast it just flickers. Lighting (sun energy/color, sky top/horizon color) is driven by one cosine-shaped brightness curve, `(cos((t - 0.5) * TAU) + 1) * 0.5` where `t` is the 0..1 fraction through the current day -- this curve mathematically bottoms out (darkest) at `t=0`/`t=1` and peaks (brightest) at `t=0.5`, so by the formula's own behavior `t=0` (the point `current_day()` itself ticks over at) is midnight, not dawn; `is_night()` straddles that same boundary (last 25% of one day through the first 15% of the next) rather than being centered on it. Every 7th day (`WAVE_INTERVAL_DAYS`), `_spawn_wave()` fires exactly once (guarded by `_last_wave_day`, since `process()` re-checks this every frame all day long): `WAVE_ENEMY_COUNT` (18) enemies, kinds picked from the *entire* `EnemyKinds` roster (not just a local chunk's biome list) for real variety, land in a ring (`WAVE_SPAWN_RADIUS`) around the player's Town Hall (or the map origin, where founder blobs start, if none is built yet) -- landing near the base is enough to trigger since `Enemy`'s own AI already chases the nearest blob within detection range, without needing a separate "damage buildings directly" mechanic the backlog item didn't specifically ask for; `GameManager`'s existing playtime-based enemy difficulty scaling makes each successive wave tougher automatically, with no extra scaling needed here. `HUD` gained a `Day N` / `Day N (Night)` readout (`hud.set_day_info`, called from `World._process` alongside the manager's own `process(delta)`), only re-punching its pulse animation when the day number actually ticks over rather than every frame. Verified via a direct-call debug hook (9 assertions, all passing): day 1 starts at midnight with `is_night()` true and sun energy at the night floor; fast-forwarding to noon flips `is_night()` false and brightens the sun to (very near) the day ceiling, confirming the cosine curve's peak lands exactly at noon; fast-forwarding to day 7 spawns exactly 18 enemies once, a second `process()` call on the same day does not double-spawn, and all spawned enemies land within the wave's own ring radius of the spawn center.
